# Dependabot PR 리뷰 스킬

의존성 업데이트 PR을 체계적으로 분석하여, 코드 변경 없이 머지 가능한지 또는 마이그레이션 작업이 필요한지 판단합니다.
리뷰만 수행하며, 코드 수정은 사용자 확인 후 별도로 진행합니다.

## 입력

사용자로부터 다음 중 하나를 받습니다:
- **GitHub PR URL** (우선): `gh pr view <URL>` 또는 `gh pr diff <URL>`로 PR 정보를 가져옵니다
- **현재 브랜치**: PR URL이 없으면 현재 체크아웃된 브랜치에서 `git diff main...HEAD`로 분석합니다

## 리뷰 워크플로우

### Phase 1: 변경 사항 파악

1. **PR 정보 수집**: PR URL이 주어지면 `gh` CLI로 diff와 메타데이터를 가져옵니다.

```bash
# PR URL이 주어진 경우
gh pr view <PR_URL> --json title,body,files
gh pr diff <PR_URL>

# 현재 브랜치에서 작업 중인 경우
git diff main...HEAD -- package.json
```

2. **패키지 매니저 감지**: `package.json`의 `packageManager` 필드 또는 lock 파일 존재 여부로 판별합니다.

| lock 파일 | 패키지 매니저 |
|-----------|--------------|
| `pnpm-lock.yaml` | pnpm |
| `package-lock.json` | npm |
| `yarn.lock` | yarn |
| `bun.lockb` / `bun.lock` | bun |

`package.json`의 `packageManager` 필드가 있으면 해당 값을 우선합니다.

3. **버전 변경 추출**: `package.json` diff에서 변경된 패키지와 버전 범위를 추출하고, semver 기준으로 분류합니다.

| 분류 | 의미 | 리뷰 수준 |
|------|------|-----------|
| patch (x.y.Z) | 버그 수정 | 낮음 — 보통 안전 |
| minor (x.Y.0) | 하위 호환 기능 추가 | 중간 — deprecation 경고 확인 |
| major (X.0.0) | breaking changes 가능 | 높음 — 반드시 상세 분석 |

### Phase 2: 패키지별 영향도 분석

각 패키지에 대해 병렬로 분석합니다. 서브에이전트를 활용해 독립적인 패키지 분석을 동시에 진행하면 효율적입니다.

#### 2-1. 코드베이스 사용처 검색

해당 패키지가 코드에서 실제로 사용되는지 확인합니다. `src/` 디렉토리와 프로젝트 루트의 스크립트 파일을 대상으로 검색합니다.

```
Grep: import.*from ['"]<패키지명>
Grep: require\(['"]<패키지명>
```

- 사용처가 없으면 → **미사용 의존성**으로 표기하고, 제거 권장 여부를 언급합니다.
- 사용처가 있으면 → 사용하는 API/함수 목록을 정리합니다.

#### 2-2. Breaking Changes 조사

major 버전 업데이트인 패키지에 대해 changelog/마이그레이션 가이드를 조사합니다.
minor 업데이트도 deprecation 경고가 있을 수 있으므로, 주요 패키지는 간단히 확인합니다.

조사 방법 (WebFetch/WebSearch 활용):
1. **GitHub releases**: `https://github.com/<owner>/<repo>/releases` — major 릴리스 노트에서 "BREAKING" 키워드 검색
2. **공식 마이그레이션 가이드**: 패키지 공식 문서에서 migration guide 검색
3. **CHANGELOG.md**: 리포지토리 내 changelog 파일

패키지의 GitHub 리포지토리 URL은 npm 레지스트리나 `package.json`의 `repository` 필드에서 확인할 수 있습니다.

#### 2-3. 영향도 매핑

찾아낸 breaking changes를 코드베이스의 실제 사용 패턴과 대조합니다.

각 breaking change에 대해:
- 우리 코드에서 해당 API/패턴을 사용하는가?
- 사용한다면 어느 파일의 몇 번째 줄인가?
- 수정이 필요하다면 구체적으로 어떻게 바꿔야 하는가? (Before/After 코드 포함)

### Phase 3: 간접 영향 분석

직접 사용하지 않더라도 다른 의존성을 통해 간접적으로 영향받을 수 있습니다.

1. **peer dependency 충돌**: 업데이트된 패키지가 다른 패키지의 peer dependency 범위를 벗어나는지 확인
2. **타입 호환성**: `@types/*` 패키지와의 버전 정합성 확인
3. **연관 패키지 정합성**: 같은 에코시스템 패키지 간 버전 호환성 (예: `prisma`와 `@prisma/client`는 동일 버전이어야 함)

### Phase 4: 검증 계획 수립

코드 수정이 필요한 경우, `package.json`의 `scripts`를 확인하여 프로젝트에 실제로 존재하는 검증 명령어만 제시합니다. `typecheck`, `build`, `test` 등의 스크립트가 없을 수 있으므로 있는 것만 나열합니다.

### Phase 5: 결론 및 후속 조치 제안

리포트를 출력한 후, 결론에 따라 사용자에게 다음 단계를 제안합니다:

- **머지 가능**: "코드 변경 없이 머지해도 안전합니다."
- **코드 수정 후 머지 가능**: "수정이 필요한 부분이 있습니다. 마이그레이션 수정 계획서를 작성할까요, 아니면 바로 코드 수정을 진행할까요?"
- **추가 논의 필요**: "리스크가 높아 추가 검토가 필요합니다. [구체적 우려사항]에 대해 논의가 필요합니다."

코드를 자동으로 수정하지 않습니다. 사용자의 선택을 기다립니다.

## 리포트 출력 형식

분석 결과를 아래 구조로 정리합니다.

```markdown
# 의존성 업데이트 리뷰

## 요약

| 패키지 | 현재 | 목표 | 유형 | 영향도 | 조치 |
|--------|------|------|------|--------|------|
| `pkg-a` | 1.0.0 | 2.0.0 | major | 높음 | 코드 수정 필요 |
| `pkg-b` | 3.1.0 | 3.2.0 | minor | 없음 | 변경 불필요 |
| `pkg-c` | 1.0.0 | 1.0.1 | patch | 없음 | 변경 불필요 |

## 결론: [머지 가능 / 코드 수정 후 머지 가능 / 추가 논의 필요]

## 패키지별 상세 분석

### `pkg-a` (1.0.0 → 2.0.0) — major ⚠️

**Breaking Changes:**
- API X가 제거됨
- 함수 Y의 시그니처 변경

**사용처:**
| 파일 | 라인 | 사용 패턴 |
|------|------|-----------|
| `src/foo.ts` | 42 | `api.oldMethod()` |
| `src/bar.ts` | 15 | `import { X } from 'pkg-a'` |

**영향 분석:**
| Breaking Change | 영향 여부 | 근거 |
|-----------------|-----------|------|
| `oldMethod()` 제거 | 영향 있음 | `src/foo.ts:42`에서 사용 중 |
| `Config` 타입 변경 | 영향 없음 | 해당 타입 미사용 |

**수정 방안:**
| 파일 | 라인 | 현재 코드 | 수정 코드 |
|------|------|-----------|-----------|
| `src/foo.ts` | 42 | `api.oldMethod()` | `api.newMethod()` |

**수정 필요 여부:** 예 — 총 N줄 수정

### `pkg-b` (3.1.0 → 3.2.0) — minor

**변경 사항:** 새 옵션 추가, 기존 API 변경 없음
**사용처:** `src/baz.ts:10` — `import { helper } from 'pkg-b'`
**영향:** 없음
**수정 필요 여부:** 아니오

## 리스크 평가

| 리스크 | 확률 | 영향 | 완화 방안 |
|--------|------|------|-----------|
| ... | ... | ... | ... |

## 검증 계획

`package.json`의 `scripts`를 확인하여 존재하는 명령어만 나열합니다:
1. `<패키지매니저> install` — 의존성 설치
2. (typecheck 스크립트가 있으면) `<패키지매니저> run typecheck`
3. (build 스크립트가 있으면) `<패키지매니저> run build`
4. (test 스크립트가 있으면) `<패키지매니저> run test`

## 후속 조치

[결론에 따른 구체적 제안]
```

## 분석 시 주의사항

- **과도한 경고 지양**: patch/minor 업데이트에 불필요한 경고를 붙이지 않습니다. 실제로 영향이 있는 것만 보고합니다.
- **미사용 의존성 식별**: 코드에서 import하지 않는 패키지는 명확히 "미사용"으로 표기하고, 제거를 권장합니다.
- **실제 코드 기반 판단**: changelog의 breaking change 목록을 그대로 나열하는 것이 아니라, 우리 코드에서 해당 API를 실제로 사용하는지 확인한 후에만 "영향 있음"으로 판정합니다.
- **구체적 수정안 제시**: "확인 필요"로 끝내지 말고, 가능한 한 Before/After 코드를 포함한 구체적 수정 방안을 제시합니다.
- **간접 의존성 주의**: 직접 import하지 않아도 다른 패키지의 내부 의존성으로 영향받을 수 있습니다. 특히 peer dependency 충돌에 주의합니다.
- **코드 수정 금지**: 이 스킬은 리뷰만 수행합니다. 수정이 필요하면 사용자에게 "마이그레이션 계획서를 작성할까요?" 또는 "바로 코드 수정을 진행할까요?"라고 물어봅니다.
