# Doc Visual Explainer

문서는 쓰는 사람의 순서로 쓰이지만, 읽는 사람은 다른 순서로 이해한다. 노션 페이지 여러 개, 리서치 노트, 대화 중에 정정된 사실이 흩어져 있으면 독자는 "그래서 핵심이 뭐고, 전체에서 이게 어디쯤이고, 나는 뭘 하면 되지?"를 스스로 조립해야 한다. 이 스킬은 그 조립을 대신한다. 원천 문서와 대화 맥락을 모아 **독자의 이해 흐름을 따라가는 한 장짜리 HTML**을 만들고, 각 내용에 맞는 시각화를 넣는다.

세 가지 원칙이 품질을 좌우한다.

1. **독자의 질문 순서대로 놓는다.** 원문 목차를 옮기지 않는다. 독자가 먼저 알아야 하는 것(요약, 전체 구조)을 앞에, 그것을 알아야 이해되는 것을 뒤에 둔다.
2. **그림 하나는 질문 하나에 답한다.** 문장이 더 빨리 전달되면 문장으로 쓴다. 그림은 메커니즘, 차이, 변화, 비율, 관계처럼 글로 조립하기 어려운 것에만 쓴다.
3. **사실은 원천과 대화에서만 가져온다.** 모르는 것은 그럴듯하게 채우지 않고 `✍️` 빈칸으로 남긴다. 대화에서 사용자가 정정한 사실이 원문보다 우선한다.

## Workflow

### Phase 0 — 독자, 상황, 목표를 정한다

대화에서 먼저 읽어 낸다. 대부분은 이미 드러나 있다.

- **누가 읽나**: 보통 사용자 본인. 팀원·면접관·리뷰어가 읽는다면 톤과 내부 정보 노출이 달라진다.
- **어떤 상황인가**: 면접 준비, 설계 리뷰, 온보딩, 의사결정, 발표 준비, 학습.
- **읽고 나서 무엇을 할 수 있어야 하나** — 한두 개만 고른다. 이 선택이 구성과 인터랙션을 정한다.

| 목표 | 페이지에 들어가는 것 |
|---|---|
| 이해: 구조·메커니즘을 설명할 수 있다 | 구조도, 흐름, 비교도. 꼬리질문/예외 |
| 기억: 핵심 숫자·답변을 외운다 | 뼈대 칩, 접힌 상세, 암기 모드(질문만 보기), 숫자 카드 |
| 결정: 선택지를 비교해 고른다 | 차이를 그린 비교도, 트레이드오프 표, 기준 |
| 실행: 할 일과 순서를 챙긴다 | 체크리스트(저장), 일정(오늘 강조), 동선 단계 |

- **시간 예산**: 5분 훑기용인지, 며칠 반복해서 볼 자료인지. 반복용이면 암기 모드와 체크리스트 저장이 값을 한다.

두 가지 해석이 서로 다른 페이지를 만들 때만 묻는다. 그 외에는 가정을 정하고 최종 보고에 한 줄로 밝힌다.

### Phase 1 — 원천을 모으고 사실 장부를 만든다

| 원천 | 방법 |
|---|---|
| 노션 URL | Notion MCP의 fetch 도구(예: `notion-fetch`). 하위 페이지는 독자의 목표에 필요한 것만 따라간다. 전부 긁지 않는다. 도구가 없으면 사용자에게 md/PDF로 내보내 달라고 한다 |
| 로컬 md/txt | Read. 길면 목차(헤딩)부터 보고 필요한 구간만 |
| PDF | Read(`pages`) 또는 `pdftotext -layout` |
| 웹 페이지 | WebFetch. 제목·날짜를 함께 기록 |
| GitHub | `gh api` (커밋 이력, 릴리스, 레포 설명) |
| 대화 | 결정, 정정, 사용자만 아는 사실. 원천으로 취급한다 |

작업용 **사실 장부**를 머릿속이나 스크래치에 둔다(페이지에 그대로 넣지 않는다). 숫자·날짜·고유명사마다 값, 출처, 기준(예: 별도/연결, 측정 방식), 확신도를 적는다.

- 출처끼리 다르면 가장 최근의 사용자 발언을 따르고, 기준이 다른 숫자는 페이지에서 단서(caveat)로 드러낸다.
- 확인 못 한 것은 `<span class="todo">✍️ 무엇을 채울지</span>`로 남긴다. 헤더가 개수를 센다. 빈칸이 보이는 페이지가 그럴듯한 오답이 섞인 페이지보다 낫다. 독자는 그 자료를 믿고 말하거나 결정하기 때문이다.

### Phase 2 — 이해 흐름을 설계한다 (HTML보다 아웃라인이 먼저)

기본 흐름은 이렇다. 주제에 맞게 줄이거나 바꾼다.

1. **한 장 요약** — 한 줄 메시지, 꼭 가져갈 것 3개, 피할 것. 여기서 멈춘 독자도 요점을 가져가야 한다.
2. **전체 지도** — 전체를 한 번에 보여 주는 그림 하나(타임라인, 관계 매트릭스, 시스템 개요). "이게 전체에서 어디쯤인가"에 답한다.
3. **주제 섹션** — 의존 순서(A를 알아야 B가 이해됨) → 우선순위(가장 중요한 것 먼저).
4. **블록 내부 순서** — 질문/주장 → 뼈대(3–5개 칩) → 그림 → 상세(접힘) → 예외·꼬리질문 → 메모.
5. **행동** — 체크리스트, 일정, 남은 빈칸, 다음 단계.

HTML을 쓰기 전에 아웃라인을 표로 만든다.

| 섹션 | 독자의 질문 | 핵심 주장 한 줄 | 시각화 | 근거 출처 |
|---|---|---|---|---|

점검: 모든 그림에 "독자의 질문"이 있는가? 그 섹션이 그 자리에 있는 이유가 있는가? 원문에는 있지만 독자의 목표에 필요 없는 내용은 빼거나 링크로만 남긴다.

### Phase 3 — 내용 유형마다 표현을 고른다

세부 사양과 코드 조각은 `references/visual-forms.md`에 있다. 고를 때는 아래 표로 충분하고, 그릴 때 해당 항목을 읽는다.

| 내용 | 표현 |
|---|---|
| 핵심 숫자 몇 개 | 숫자 카드(tiles). 측정 기준이 다르면 같은 축에 두지 말고 카드 + 단서 |
| 실제 순서가 있는 절차 | 번호 단계(steps). 순서가 정보가 아니면 번호를 쓰지 않는다 |
| 흐름·인과·병목 | 흐름 칩(flowrow). 병목·핵심은 강조 칩 |
| 무엇이 바뀌었나(전/후) | 두 줄 흐름 칩 또는 덤벨 차트 |
| 범주별 크기 | 막대(≤24px, 끝 4px 둥글게, 값은 끝에) |
| 시간에 따른 변화 | 선(2px, 점은 실제 데이터 시점에만, 간격 불균등이면 시간 축에 맞춰) |
| 전체 중 비율 | 세그먼트 막대 + 범례 + 표로 보기 |
| 기간·이력 | 간트형 타임라인 + 사건 표시선 |
| 메커니즘·아키텍처 | 박스-화살표 구조도. 화살표에 "무엇이 오가는지" 동사 라벨 |
| 두 선택지 비교 | 나란한 구조도로 **차이(추가·제거되는 선 하나)**를 그린다 |
| 저수준 원리(메모리, 패킷 등) | 셀·격자 그림 |
| 항목 × 범주 대응 | 점 매트릭스(● 대표 / ○ 보조) |
| 정확한 값을 찾아봐야 함 | 표 |
| 외워야 하는 답변 | 뼈대 칩 + 접힌 상세 + 암기 모드 |
| 독자가 실측값을 넣을 것 | 작은 계산기(예시 값은 "예시" 태그로 표시) |
| 할 일 | 저장되는 체크리스트, 오늘 날짜 강조 일정 |

`dataviz`·`artifact-diagramming` 스킬이 설치돼 있으면 함께 쓴다. 실제 숫자 차트는 `dataviz`의 마크 사양과 팔레트 검증을, 구조도는 `artifact-diagramming`의 원칙(메커니즘을 그려라, 차이를 그려라, 화살표에 라벨)을 따른다. 없으면 `references/visual-forms.md`의 규칙만으로 충분하다.

### Phase 4 — 디자인

`assets/template.html`을 복사해서 시작한다. 토큰, 라이트/다크, 컴포넌트 CSS, 툴팁, 세그먼트 막대 렌더러, 저장되는 입력, 암기 모드, 모두 펼치기, 섹션 탭 강조, 오늘 날짜 강조, 빈칸 개수 세기가 들어 있다. 예시 블록(`EXAMPLE` 주석)은 실제 내용으로 바꾸거나 지운다.

- **색**: 강조색은 주제의 세계에서 고른다(회사·제품·분야와 어울리되 로고나 브랜드를 흉내 내지 않는다). 중성색은 강조색 쪽으로 살짝 기운 회색. 색의 역할을 섞지 않는다 — 강조(핵심), 빨강(채울 빈칸), 상태색(좋음/위험, 아이콘·라벨과 함께), 차트 계열색(정체성)은 각각 따로 쓴다. 글자는 차트 계열색으로 칠하지 않는다.
- **차트 계열색**: 템플릿의 `--s1`~`--s5`는 색각 이상 구분과 대비를 라이트(#ffffff)·다크(#1a1c16) 바탕에서 검증한 값이다. 계열색이나 `--surface`를 바꾸면 `dataviz` 스킬의 `validate_palette.js`로 다시 검증한다. 검증 도구가 없으면 계열색과 `--surface`는 그대로 두고 강조색·중성색만 바꾼다. 라이트에서 3:1이 안 되는 색(aqua·yellow·magenta)은 직접 라벨이나 "표로 보기"를 함께 둔다. 계열색 칸 안의 글자는 s1 위에서만 `--on-s1`, 나머지 위에서는 진한 글자다(템플릿에 반영돼 있다).
- **글꼴**: 제목용 개성 있는 글꼴은 제목에만, 본문은 그 언어에서 잘 읽히는 글꼴, 숫자·ID는 고정폭. 한국어 기본은 Hahmlet + IBM Plex Sans KR + IBM Plex Mono. 영어는 주제에 맞는 조합을 고르되 Inter·Space Grotesk 같은 무난한 기본값은 피한다. 모든 글꼴에 대체 글꼴 스택을 둔다.
- **피할 것**: 크림 바탕 + 테라코타, 거의 검정 + 형광 초록, 보라-파랑 그라데이션 히어로, 이모지 섹션 표시, 전부 가운데 정렬, 모든 블록에 같은 그림자·둥근 모서리, 둥근 카드 왼쪽의 강조 막대.
- 라이트/다크 모두 토큰으로 정의하고 `body` 배경을 토큰으로 칠한다(템플릿 구조 유지).

### Phase 5 — 작성 규칙

- **한 파일**에 CSS와 JS를 넣는다. 외부는 Google Fonts만(정말 필요하면 버전을 고정한 CDN 라이브러리). 로컬에서 바로 열리도록 doctype까지 갖춘 완전한 문서로 쓴다. 나중에 아티팩트로 올릴 때는 doctype·html·head·body 태그를 걷어 낸다.
- **SVG**
  - `viewBox`를 내용에 맞추고 CSS로 크기를 조절한다. 넓은 그림은 `.fig-scroll`(+`w640` 등 최소 폭)에 넣어 페이지가 가로로 스크롤되지 않게 한다.
  - 색은 클래스로 준다. `stroke="var(--x)"`처럼 **표현 속성 안의 CSS 변수는 브라우저마다 무시될 수 있다** → `class` 또는 `style="stroke:var(--x)"`.
  - 화살표 마커 id는 그림마다 고유하게(`ah-<그림이름>`).
  - 글자 11–13px. 폭은 한글 ≈ 1em, 라틴 ≈ 0.6em으로 어림하고 선·박스와 6px 이상 띄운다. 선은 박스를 피해 직각으로 돌리고, 박스를 관통시키지 않는다. 사건 표시선이 라벨을 가로지르지 않게 라벨을 줄이거나 옮긴다.
  - `role="img"`와 `aria-label`에 그림의 주장을, `<figcaption>`에 같은 주장을 쓴다.
- **인터랙션은 목표에 맞을 때만**: 차트에는 툴팁 + "표로 보기"(마우스 없이도 값이 보이게). 기억 목표면 암기 모드. 계산기는 독자가 실제 값을 넣을 때만. 체크리스트와 입력은 `localStorage`(페이지별 접두사)에 저장하고 실패해도 페이지가 돌아가게 한다.
- **민감한 개인 값**(연봉 기준 등)은 페이지에 적지 않고 입력칸으로만 둔다.
- 글은 짧고 직접적으로. 독자가 소리 내어 말할 문장이면 실제로 말하는 문장으로 쓴다.

### Phase 6 — 검증 (한 번 보고, 한 번 고친다)

1. 구조 검사:
   ```bash
   python3 <skill-dir>/scripts/check_html.py <file.html>
   ```
   태그 짝, 중복 id, 스크립트 문법(node), SVG 속성 안의 `var()`, 허용되지 않은 외부 리소스, 빈칸 개수(`<main>` 안, 페이지 헤더가 세는 것과 같은 기준), 파일 크기를 본다. 오류는 고치고 다시 돌린다.
2. 렌더링 한 번:
   ```bash
   <skill-dir>/scripts/preview_server.sh start <file.html> [port]   # URL 출력. 기본 포트 8765
   ```
   포트가 이미 쓰이고 있거나 서버가 뜨지 않으면 URL 없이 exit 1로 끝난다. 그때는 다른 포트를 세 번째 인자로 준다. 브라우저 자동화 도구(Playwright MCP 등)로 그 URL을 연다(`file://`은 막혀 있다). 긴 페이지의 전체 스크린샷은 약 16,000px를 넘으면 타일이 반복돼 보인다(페이지 문제 아님). 섹션별 요소 스크린샷(`target: "#섹션id"`)으로 본다. 볼 것: 선을 가로지르는 라벨, 박스를 넘치는 글자, 겹친 마크, 다크 모드 가독성, 콘솔 오류.
3. 보이는 문제를 한 번에 고친 뒤 `preview_server.sh stop`. 사용자 폴더에 생긴 `.playwright-mcp/` 파일 중 내가 만든 것은 지운다. 확인을 반복하지 않는다. 큰 문제가 남으면 보고한다.

브라우저 도구가 없으면 2단계는 건너뛰고, 건너뛰었다고 보고한다.

### Phase 7 — 전달

- **저장 위치**: 원천이 로컬 파일이면 같은 폴더에 `<원본이름 또는 주제>.html`. 노션·웹이면 현재 작업 폴더. 같은 이름의 파일이 있으면 확인하고 덮어쓴다.
- **보고**: 절대 경로, 섹션 × 시각화 × 무엇을 돕는지 표, 인터랙션, 검증한 것, 남은 ✍️ 개수와 중요한 것 몇 개. 아티팩트 게시 기능이 있는 환경이면 마지막 한 줄로 비공개 게시(휴대폰에서 보기)를 제안한다.
- **이후 정정**: 사용자가 사실을 고치면, 이번 작업에서 만든 **모든 사본**(HTML, 같이 만든 노션·md)을 같은 턴에 함께 고치고 `check_html.py`를 다시 돌린다. 한쪽만 고치면 다음에 어느 쪽이 맞는지 알 수 없게 된다.

## 예시 사례 (규모 감각용 · 가상의 시나리오)

동네 도서관 무인 반납기 도입 보고서(노션 페이지 6개) + 이용 통계 md 2개 + 대화 정정 사항 → HTML 1개(약 150KB).

- 독자/목표: 운영위원회에서 결과를 발표할 담당자 본인, 기억 + 실행. 그래서 암기 모드, 뼈대 칩, 접힌 답변, 발표일 D-day, 저장되는 체크리스트를 넣었다.
- 흐름: 한 장 요약 → 전체 지도(운영 기간 간트 + 지표×예상 질문 매트릭스) → 예상 질문별 섹션 → 처리 흐름 구조도 → 발표 준비 체크.
- 그림: 운영 기간 간트(사건 표시선), 도입 전/후 흐름 칩, 무인 반납 비율 선 그래프, 지점별 막대, 덤벨, 알림 경로 세그먼트 막대, 반납기 → 분류 → 서가 박스-화살표 구조도, 두 배치안 비교도, 처리 시간 계산기.
- 이후 사용자가 숫자·날짜를 여러 번 정정했고, 그때마다 HTML·노션·md를 함께 고쳤다.
