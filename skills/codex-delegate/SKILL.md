# codex-delegate — Codex CLI 개발 위탁·오케스트레이션

## 역할 분담

이 스킬의 목적은 구현 노동을 Codex에 위탁해서 이 세션(Claude)이 본질 — 설계 판단, 범위 통제, 결과 검증 — 에 집중하는 것입니다. 역할은 발주자와 시공자 관계입니다:

- **Claude (발주자·감독)**: 계획을 위탁 단위로 분해하고, 위탁 프롬프트를 작성하고, 실행을 관리하고, 결과물을 검증·통합합니다. **최종 품질 책임은 위탁 후에도 이 세션에 있습니다.** 검증 없이 "위탁 완료"라고 보고하지 마세요.
- **Codex (시공자)**: 프롬프트에 명시된 계획대로 코드를 작성·수정하고 자체 검증 후 보고합니다.

Codex는 이 대화를 볼 수 없습니다. 위탁 프롬프트가 Codex의 유일한 정보원이므로, 대화 속 맥락(계획, 사용자의 제약, 결정 사항)을 프롬프트에 전부 옮겨 담아야 합니다.

## 0단계 — 사전 점검

1. **Codex 확인**: `codex --version`. 미설치·미로그인이면 중단하고 사용자에게 `! codex login` 등을 안내.
2. **모델 확인**: `~/.codex/config.toml`의 `model` 값이 사용자가 유지하는 최신 모델입니다. 특별한 이유가 없으면 `-m`으로 덮어쓰지 말고 config 기본값을 그대로 쓰세요. 단, config의 모델이 명백히 구세대라면(예: deprecated 공지) 사용자에게 알리세요.
3. **계획 확인**: 승인된 계획이 있는지 확인하세요 — 대화 속 플랜, 플랜 문서 파일, 이슈 코멘트 등. 계획 없이 위탁하면 Codex가 설계까지 스스로 하게 되어 통제를 잃습니다. 계획이 없으면 위탁 전에 계획부터 세우거나 사용자에게 확인하세요.
4. **작업 기록 디렉토리**: 위탁 실행 기록(프롬프트, 로그, 최종 보고)은 scratchpad 아래 `codex-runs/<작업명>/`에 남깁니다.

## 1단계 — 위탁 단위 결정 (단독 vs 병렬)

계획을 보고 스스로 판단하세요. 기본값은 **단독 위탁**입니다. 병렬은 이득이 명확할 때만 선택합니다.

**병렬이 유리한 조건 (모두 충족할 때):**
- 작업들이 서로 다른 모듈·디렉토리에 속해 **수정 파일이 겹치지 않음**
- 작업 간 **순서 의존성이 없음** (A의 결과물을 B가 import하지 않음)
- 각 작업이 독립적으로 테스트 가능
- 각 작업이 병렬화 오버헤드(worktree 생성·통합·충돌 해결)를 상회할 만큼 큼

**단독이 맞는 조건 (하나라도 해당하면):**
- 순차 의존성이 있거나 같은 파일을 여러 작업이 수정
- 전체가 1~2개 파일 수정 수준으로 작음
- 공유 계약(스키마, API 명세) 변경이 작업의 중심

**공유 계약 파일 규칙 (병렬 충돌의 대부분을 없애는 규칙):**
OpenAPI 명세, DB 스키마, 라우트 인덱스, 공용 타입 정의처럼 여러 작업이 손대는 파일은 병렬 위탁 대상에서 **제외**하고, 위탁 전에 Claude가 직접 확정하거나 선행 단독 위탁으로 먼저 처리하세요. 그 결과(확정된 인터페이스)를 각 병렬 프롬프트에 명시합니다.

병렬 분할은 **2~4개**를 권장합니다. 그 이상은 통합 비용이 분업 이득을 잠식합니다.

판단 결과(단독/병렬, 분할 근거)를 사용자에게 한 문단으로 보고한 뒤 진행하세요.

## 2단계 — 위탁 프롬프트 작성

`references/delegation-prompt.md`를 읽고 템플릿대로 작성하세요. 핵심 구성: 프로젝트 컨텍스트 → 구현 계획 전문 → 범위 제한 → 완료 기준(검증 명령 포함) → 보고 형식.

계획이 파일로 존재하면(예: design-review를 거친 플랜 문서) 전달 방식은 규모로 정하세요 — 기준과 이유는 `references/delegation-prompt.md`의 "계획 파일 전달" 절 참고. 요지: 보통 규모면 전문을 프롬프트에 포함(기본), 크면 태스크 관련 섹션 발췌 + 파일 가용성 보장 + 완독 지시. 병렬 위탁이면 어느 쪽이든 전체 목표·확정 인터페이스 같은 공통 컨텍스트는 각 프롬프트에 유지합니다.

프롬프트는 반드시 **파일로 저장**하세요 (`codex-runs/<작업명>/prompt.md`). 쉘 이스케이프 문제를 피하고 재실행·재지시 시 기록이 됩니다.

## 3단계 — 실행

**reasoning effort 결정** — 기본은 `high`. 다음 중 하나에 해당하면 `xhigh`:
- 다수 파일에 걸친 리팩토링·마이그레이션 등 놓치는 지점이 생기기 쉬운 작업
- 동시성, 보안, 데이터 정합성 등 실수 비용이 큰 작업
- 같은 작업의 이전 위탁이 실패한 재시도

애매하면 `high`를 쓰세요. xhigh는 느리고 비싸므로 근거가 있을 때만 올립니다.

**실행 방법** — 번들 스크립트를 백그라운드로 실행합니다:

```bash
bash ~/.claude/skills/codex-delegate/scripts/codex_run.sh \
  <run-dir> <workdir> <prompt-file> [effort] [model]
```

- 단독 위탁: `workdir`는 저장소 루트, Bash `run_in_background: true`로 실행.
- 병렬 위탁: `references/parallel-orchestration.md`를 읽고 worktree를 준비한 뒤, **같은 턴에** 모든 태스크를 백그라운드로 스폰하세요.

실행 중에는 대기하지 말고 검증 준비(리뷰 관점 정리, 테스트 시나리오 확인)나 사용자와의 다음 논의를 진행하세요. 완료되면 백그라운드 작업 알림이 옵니다.

## 4단계 — 모니터링

- 진행 확인이 필요하면 `<run-dir>/run.log`를 tail 하세요.
- `<run-dir>/last-message.md`가 Codex의 최종 보고입니다.
- `run.log` 상단 배너에 `session id`가 있습니다. 추가 지시가 필요하면 새 세션 대신 `codex exec resume <session-id> "<추가 지시>"`를 쓰세요 — 기존 세션이 작업 컨텍스트를 그대로 갖고 있습니다.
- 장시간(작업 규모 대비 과도하게) 무출력이면 로그를 확인하고, 멈춘 것으로 판단되면 프로세스를 정리하고 재실행하세요.

## 5단계 — 검증 (생략 금지)

Codex의 보고를 그대로 믿지 마세요. 직접 확인합니다:

1. **diff 리뷰**: `git diff`로 전체 변경을 훑으세요. 확인 관점 — 계획 범위 밖 변경은 없는가, 프로젝트 컨벤션(에러 처리, 네이밍, 패턴)을 따랐는가, 테스트를 약화(스킵·단언 제거)하지 않았는가.
2. **검증 명령 실행**: 프로젝트의 테스트·빌드·린트를 직접 실행하세요. Codex가 "통과했다"고 보고했어도 재실행합니다.
3. **실패 시 재지시**: 문제를 구체적으로(파일, 증상, 기대 동작) 적어 `codex exec resume`으로 재지시하세요. **같은 문제로 2회 실패하면** 재위탁을 멈추고 Claude가 직접 수정하는 것이 보통 더 빠릅니다.

## 6단계 — 통합과 보고

- 병렬 위탁이었다면 `references/parallel-orchestration.md`의 통합 절차대로 브랜치를 병합하고, 병합 후 전체 테스트를 다시 실행하고, worktree를 정리하세요.
- 사용자에게 보고: 무엇을 어떻게 위탁했는지(단독/병렬, effort), Codex가 변경한 내용 요약, **직접 실행한 검증 결과**, 계획과 달라진 점, 남은 이슈. 커밋은 사용자가 요청할 때만 합니다.

## 번들 리소스

- `scripts/codex_run.sh` — codex exec 실행 래퍼 (로그·최종 보고·종료 코드 수집)
- `references/delegation-prompt.md` — 위탁 프롬프트 템플릿과 작성 원칙
- `references/parallel-orchestration.md` — worktree 기반 병렬 오케스트레이션 절차
