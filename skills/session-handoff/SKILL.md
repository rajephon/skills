# Session Handoff

긴 세션은 결국 끝나고, 후속 작업은 흔히 새 세션에서 이어진다. 새 세션은 이전 대화를 전혀 모르므로, 사람이 매번 맥락을 다시 설명하거나 — 더 흔하게는 — 중요한 결정·계약을 빠뜨린 채 시작한다. 이 skill은 그 인계를 한 번에 처리한다: **새 세션 첫 메시지에 그대로 붙여넣으면 바로 이어서 일할 수 있는 자족적 프롬프트**를 만들어 임시 파일로 저장하고 경로를 알려준다.

핵심 철학은 두 가지다.

1. **사용자가 다음 작업을 정한다.** 인계의 목적은 "직전에 하던 걸 그대로"가 아니라 "다음에 할 것"이다. 다음 Phase일 수도, 후속 이슈일 수도, 방금 작업에서 갈라져 나온 별개 작업일 수도 있다. 사용자 지정을 우선하되, 없으면 현재 세션의 자연스러운 다음 단계를 추론해 제안하고 확인받는다.

2. **중복 명세하지 않는다.** 이슈·플랜·PR·설계 문서·코드는 새 세션이 도구로 직접 열어볼 수 있다. 이런 것을 프롬프트에 복제하면 (a) 길어지고 (b) 원본과 어긋날 위험이 생긴다. 그러니 **링크로 남긴다.** 인라인으로 적는 건 *직전 세션에서만 생겼고 어디에도 기록되지 않은* 맥락뿐이다. 이 판단이 이 skill의 품질을 좌우한다 (아래 Phase 2).

## Workflow

### Phase 0: 인계할 작업 확정

사용자가 작업을 지정했으면(예: "Phase 2 진행", "이 리뷰 코멘트 반영", "#142 이어서") 그것을 중심으로 한다. 모호하거나 비어 있으면, 현재 세션에서 추론한 다음 단계를 한 줄로 제안하고 확인받는다 — "다음 세션에서 *X*를 진행하는 걸로 프롬프트를 만들까요?"

**확인 없이 바로 만들어야 하거나, 그럴듯한 후속이 둘 이상이면** — 가장 합리적인 것 하나를 골라 진행하되 *그것이 추론한 가정임을 프롬프트 안에 드러낸다.* 새 세션이 "확정된 지시"로 오해하지 않도록 첫머리에 "(다음 작업을 *X*로 가정함 — 아니면 알려줘)" 식으로 표시하고, 함께 떠오른 다른 후속 후보는 '미해결/주의'에 한 줄씩 남겨 사용자·새 세션이 방향을 틀 수 있게 한다. 이것이 정보 덤프(지금까지 한 일을 통째로 넘기기)와의 결정적 차이다 — 인계는 *다음 행동 하나*에 초점을 맞추되, 그 선택이 잠정적임을 숨기지 않는다.

작업이 무엇을 산출해야 끝나는지(완료 조건), 어떤 레포·디렉토리에서 도는지도 같이 확정한다. 이게 프롬프트의 첫 문장과 시작 방법을 결정한다.

### Phase 1: 컨텍스트 수집

현재 세션과 작업 공간에서 다음을 모은다. **대화 히스토리를 먼저 훑고**, 빠진 것만 도구로 확인한다(git 상태, 이슈/PR 조회 등).

- **1차 진입점**: 다음 작업이 걸려 있는 이슈/티켓 URL, 플랜 문서 경로, 또는 (없으면) 작업 설명 자체
- **참조 링크**: 부모/형제 이슈, 관련 PR, 설계·리뷰 문서, 스펙 파일 — 새 세션이 열어볼 만한 모든 출처
- **레포·브랜치**: 작업 레포, 브랜치 전략(새 브랜치? 기존 브랜치?), 크로스 레포면 각 레포 역할
- **직전 세션에서만 생긴 맥락** (Phase 2에서 선별): 확정된 설계 결정, 다음 작업이 의존하는 인터페이스/데이터 계약, 코드·설계 리뷰에서 나온 발견, 미해결·보류 사항, 재사용할 코드 포인터, 알려진 함정

### Phase 2: 무엇을 링크로, 무엇을 인라인으로 (핵심 판단)

이 분류가 좋은 handoff와 장황한 handoff를 가른다. 기준은 **"새 세션이 그 정보를 다른 곳에서 얻을 수 있는가?"** 다.

**링크로 남길 것** (새 세션이 직접 열어볼 수 있음 → 복제 금지):
- 이슈/티켓 본문, 부모·형제 이슈 → URL
- 플랜·설계 문서(`docs/plans/...` 등) → 경로
- PR(설명·변경·리뷰 코멘트 포함) → URL
- 스펙·스키마·API 문서 → 경로
- 이미 이슈 코멘트나 플랜에 기록해 둔 결정 → 그 위치 링크

**인라인으로 담을 것** (직전 세션에서만 존재 → 적지 않으면 유실):
- 대화 중 내려졌지만 아직 문서화 안 된 설계 결정
- 다음 작업이 *반드시* 지켜야 하는 인터페이스/데이터 계약 — 짧게 요약 + 출처 링크. 예: "recipient 필드는 백엔드 `sendNotification()` 인자와 1:1 매핑"
- 리뷰·디버깅에서 드러난 사실(함정, 제약, 실패 원인)
- 미해결 질문, 보류된 결정, "다음 세션이 모르면 실수할 것"
- 재사용 코드 포인터(파일·함수) — 단 **"출발점일 뿐, 직접 재확인"** 톤으로. 세션 사이에 코드가 바뀌었을 수 있어 단정값으로 주면 새 세션이 틀린 전제를 신뢰한다

판단이 서지 않으면 자문한다: *"이걸 빼면 새 세션이 링크만 보고 스스로 알아낼 수 있나?"* 그렇다면 링크로. 아니라면 인라인으로. 인라인은 짧게, 가능하면 출처 링크를 곁들인다.

### Phase 3: 프롬프트 작성

아래 구조를 기본으로 하되, 작업 성격에 맞춰 가감한다. 빈 섹션은 넣지 않는다 — 인라인 맥락이 없으면 그 섹션을 통째로 생략한다(억지로 채우지 않는다).

```markdown
[작업 한 줄 요약 + 1차 진입점 링크]

[새 세션이 첫 행동으로 무엇을 할지 — 예: "이 이슈를 issue-planner로 플래닝해줘",
 "이 PR 리뷰 코멘트를 반영해줘". 트리거할 스킬/도구가 있으면 자연스럽게 유도]

## 참조 (링크만 — 본문 복제 금지)
- 이슈/티켓: <url>
- 부모/형제 이슈: <url>
- 플랜 문서: <경로>
- 관련 PR: <url>

## 선행 맥락 (직전 세션 결과 — 새 세션이 모르는 것만)
[확정된 산출물·상태를 짧게. 상세는 위 링크로]

## 지켜야 할 계약 / 결정
[다음 작업이 의존하는 인터페이스·데이터 계약·설계 결정. 짧게 + 출처]

## 재사용 포인터 (출발점 — 직접 재확인 권장)
[파일·함수 경로. "Phase X 분석 시 파악, 코드 변경됐을 수 있으니 확인" 톤]

## 미해결 / 주의
[보류 결정, 알려진 함정, 다음 세션이 놓치면 실수할 것]
```

작성 원칙:
- **첫 문장은 행동 가능해야 한다.** 정보 덤프가 아니라 "무엇을, 어디서, 어떻게 시작"이 첫머리에 온다.
- **새 세션의 첫 스킬을 의식한다.** 후속이 이슈 기반이면 이슈 URL + 플래닝 요청을 넣어 `issue-planner` 류가 자연스럽게 트리거되게 한다. 코드 작업이면 레포·브랜치·진입 파일을 준다.
- **재사용 포인터·계약은 "직접 재확인" 톤.** 파일/라인은 출발점으로만 — 세션 간 코드가 바뀌었을 수 있다.
- **링크가 본문을 대신한다.** 이슈/플랜에 있는 내용을 다시 풀어쓰지 않는다.
- **다음 작업이 추론이면 숨기지 않는다.** 사용자가 명시하지 않아 추론한 경우, 첫머리에 가정임을 표시하고 진지한 대안 후보를 '미해결/주의'에 남긴다 (Phase 0).

### Phase 4: 임시 파일 저장 + 경로 출력

프롬프트를 임시 디렉토리의 `initial-prompt.md`로 저장한다. 충돌을 피하려고 고유 디렉토리를 만든다:

```bash
HANDOFF_DIR=$(mktemp -d "${TMPDIR:-/tmp}/handoff-XXXXXX")
# 작성한 프롬프트를 "$HANDOFF_DIR/initial-prompt.md" 로 저장 (Write 도구 사용)
echo "$HANDOFF_DIR/initial-prompt.md"
```

저장 후 사용자에게:
- 저장 경로 (예: `/tmp/handoff-a1b2c3/initial-prompt.md`)
- 새 세션을 열고 그 파일 내용을 첫 메시지로 붙여넣으면 됨을 한 줄 안내
- 프롬프트 본문도 채팅에 함께 보여줘 사용자가 바로 검토·복사할 수 있게 한다 (`/copy`로 복사 가능)

## 예시

**입력 (사용자):** "Phase 1 끝났고 PR 머지했어. 새 세션에서 Phase 2 진행할 프롬프트 만들어줘."

**좋은 출력** — 이슈·플랜은 링크, 직전 세션의 데이터 계약만 인라인:

```markdown
알림 발송 파이프라인 **Phase 2** (이슈 #42)를 진행하려고 해.
https://github.com/org/repo/issues/42

이 이슈를 issue-planner로 분석하고 구현 계획을 세워줘. 설계가 크면 design-review까지.

- 부모 이슈(전체 Phase 그림): https://github.com/org/repo/issues/40
- Phase 1 플랜: docs/plans/issue-41-notification-templates.md

## 선행 맥락 (Phase 1 산출물)
- `notification-templates.json` 생성·머지됨 — 채널별 알림 템플릿 정의. 상세 스키마는 위 PR/플랜 참조

## 지켜야 할 계약
- recipient 필드는 백엔드 `sendNotification()` 인자와 1:1 매핑 (channel/locale/...)
- channel:null 불가 — 미지정 사용자는 defaultChannel:"email"이 부여됨. optedOut:true는 발송 대상에서 제외

## 재사용 포인터 (직접 재확인)
- src/notifications/index.ts processNotificationJob() — 발송 흐름 진입점
- src/notifications/job-processor.ts buildRecipientsFromGroups() — 그룹 수신자 펼치기
```

여기서 핵심: recipient 스키마 전체나 이슈 본문을 복제하지 않았다 — 링크가 그 역할을 한다. 인라인된 건 *플랜에도 다 적혀 있지만 다음 작업이 즉시 의존하는 계약 요약*과 *재확인용 코드 포인터*뿐이다.

**나쁜 출력** — 이슈 본문·플랜 내용·스키마 전체를 그대로 복붙해 200줄이 되고, 원본이 바뀌면 어긋나며, 정작 "다음 세션이 모르면 실수할 계약"은 묻혀 버린다.
