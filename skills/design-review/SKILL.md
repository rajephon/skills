# Design Review Cycle

설계/플랜 문서에 대해 전문가 에이전트 리뷰 → 피드백 수용/거절 판단 → 플랜 업데이트 → 재리뷰를 승인까지 반복.

## Workflow

```
플랜 문서 확인 → REVIEW → TRIAGE → UPDATE → RE-REVIEW ─→ 승인: 종료
                                                └─→ 미승인: TRIAGE로 복귀
```

## Phase 1: Review

Task tool로 `oracle` 에이전트를 스폰하여 리뷰 요청.

### 에이전트 프롬프트 구성

```
당신은 {전문가 유형, 기본: 10년 이상 경력의 시니어 백엔드 엔지니어}입니다.
{전문 분야}에 전문성을 가지고 있습니다.
다음 설계안에 대해 엄격하고 심도 있는 설계 리뷰를 수행해주세요.

## 리뷰 대상
{플랜 요약 또는 파일 경로}

## 관련 코드 (실현 가능성 검증용)
{관련 파일 목록 — 에이전트가 직접 Read하도록}

## 리뷰 체크리스트
{도메인별 체크리스트 — 아래 참조}

## 응답 형식
각 항목: ✅ 문제없음 / ⚠️ 개선 권장 / 🚨 반드시 수정 + 구체적 근거
최종 결론: 승인 / 조건부 승인 / 반려
우선순위별 액션 아이템: P0(반드시) / P1(권장) / P2(선택)

한국어로 작성해주세요.
```

### 리뷰 체크리스트 (도메인별 조합)

**백엔드 설계**:
1. Race Condition & 동시성
2. 데이터 정합성
3. 에러 복구 & Edge Cases
4. API 설계 적절성
5. 기존 시스템과의 통합
6. 확장성 & 운영
7. 테스트 커버리지

**프론트엔드 설계**: 상태 관리, 렌더링 성능, 접근성, UX 일관성

**인프라/DevOps**: 가용성, 장애 복구, 비용, 보안, 모니터링

**DB 설계**: 정규화, 인덱스, 마이그레이션 안전성, 쿼리 성능

사용자가 관점을 지정하면 해당 항목만 집중.

## Phase 2: Triage

리뷰 피드백을 받으면 각 항목을 독립적으로 판단한다.

### 판단 전 필수 검증

피드백에서 언급된 코드를 **실제로 확인**한다 (Explore/Read 사용).
리뷰어의 전제가 맞는지 검증 후 판단.

### 분류 기준

| 분류 | 기준 | 플랜 반영 |
|------|------|-----------|
| ✅ 수용 | 기술적으로 타당 + 실현 가능 + 코드 확인됨 | 플랜 본문 수정 |
| ❌ 거절 | 아래 근거 중 하나 이상 해당 | 거절 사유 기록 |
| 📌 별도 이슈 | 타당하지만 이 피쳐 범위 밖 | "범위 밖" 섹션에 추가 |

### 거절 가능 근거

- **YAGNI**: 현재 불필요한 기능
- **과도한 설계**: 복잡도 대비 가치 낮음
- **범위 밖**: 기존 pre-existing issue
- **기술적 오류**: 리뷰어 전제가 코드 확인 결과 틀림
- **비용 > 가치**: 구현 비용이 이점 초과

## Phase 3: Update

플랜 파일을 직접 수정한다.

### 필수 반영 항목

1. frontmatter `review_round` 증가
2. "설계 리뷰 피드백 반영 (Round N)" 섹션 추가:

```markdown
## 설계 리뷰 피드백 반영 (Round N)

### ✅ 수용
| # | 피드백 | 수용 근거 | 반영 위치 |
|---|--------|-----------|-----------|

### ❌ 거절
| # | 피드백 | 거절 근거 |
|---|--------|-----------|

### 📌 별도 이슈로 분리
| # | 피드백 | 분리 근거 |
|---|--------|-----------|
```

3. 수용된 피드백을 **플랜 본문에 실제로 반영** (섹션만 추가하고 본문 미수정하면 안 됨)
4. 거절된 피드백을 "거절된 피드백 기록" 섹션에 근거와 함께 기록

## Phase 4: Re-review

업데이트된 플랜에 대해 새 oracle 에이전트를 스폰하여 재리뷰 요청.

### 재리뷰 프롬프트 차별점

이전 라운드와 달리 다음에 집중하도록 지시:
1. 수용된 피드백이 **올바르게** 반영되었는가
2. 거절 사유가 **합리적**인가
3. 이전 리뷰에서 **놓친** 이슈가 있는가
4. 플랜 전체 **일관성** (모순, 빠진 파일, 의존성 오류)

### 종료 조건

- **승인** → 사이클 종료. 사용자에게 전체 라운드 요약 보고.
- **조건부 승인** → Phase 2로 복귀.
- **반려** → Phase 2로 복귀. 근본적 재설계 필요 시 사용자에게 확인.

## 결과 보고

각 라운드 종료 시 사용자에게 보고:

```
## N차 리뷰 결과: [승인/조건부 승인/반려]

### 🚨 P0 (N건)
| # | 항목 | 설명 |

### ⚠️ P1 (N건)
| # | 항목 | 설명 |

### 💡 P2 (N건)
| # | 항목 |

### ✅ 문제없음
- 항목들...
```

최종 승인 시 전체 사이클 요약:

```
## 리뷰 프로세스 요약

| 라운드 | 결론 | 발견 이슈 | 수용 | 거절 |
|--------|------|-----------|------|------|
| 1차 | 조건부 | N건 | N건 | N건 |
| 2차 | 승인 | 0건 | - | - |
```
