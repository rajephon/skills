# Expert Code Review

코드 변경사항에 대한 3인 전문가 병렬 리뷰 → 수용/거절 판단 → 코드 반영 → 재리뷰 사이클.

## Workflow

```
코드 변경 파악 → REVIEW (3 oracle 병렬) → TRIAGE (수용/거절) → IMPLEMENT (수용건 반영)
                                                                    ↓
                                               RE-REVIEW (거절 사유 검증 + 반영 확인) → 완료
```

## Phase 1: 리뷰 대상 파악

변경된 파일 목록을 확인한다. 사용자가 파일을 지정하지 않은 경우:

```bash
git diff --name-only HEAD   # staged + unstaged
git diff --cached --name-only  # staged only
```

각 파일을 Read하여 변경 내용을 파악한다. 관련 인터페이스, 테스트, 설정 파일도 함께 확인한다.

## Phase 2: 3인 전문가 병렬 리뷰

Agent tool로 3개의 `oracle` 에이전트를 **동시에** 스폰한다. 각 에이전트는 서로 다른 전문 관점을 가진다.

### 리뷰어 구성

| 리뷰어 | 관점 | 핵심 체크포인트 |
|--------|------|----------------|
| 보안/에러처리 | 취약점, 에러 처리, 로깅 보안, 환경변수 | XSS, 인젝션, PII 노출, API 키 보호, 예외 처리 누락 |
| 코드품질/패턴 | 프로젝트 패턴 준수, DI, SOLID, DRY, 네이밍 | 기존 코드와의 일관성, 중복, 타입 안정성, 아키텍처 정합성 |
| 테스트 커버리지 | 분기 커버리지, 테스트 품질, 격리, 패턴 | 누락 분기, stub 전략, 엣지 케이스, flaky test 위험 |

사용자가 관점을 지정하면 해당 구성으로 조정.

### 에이전트 프롬프트 템플릿

각 에이전트에게 다음을 포함하여 프롬프트:

```
당신은 **{관점} 전문 코드 리뷰어**입니다.

## 리뷰 대상 파일들
{변경 파일 목록 + 설명}

## 기존 코드 참조 ({비교 목적})
{인터페이스, 유사 구현체, 테스트 패턴 등}

## 리뷰 관점
{해당 리뷰어의 체크포인트 목록}

## 출력 형식
각 이슈를 아래 형식으로 작성:

### [심각도: Critical/Major/Minor/Nit] 이슈 제목
- **파일**: 파일 경로:라인 번호
- **문제**: 무엇이 문제인지
- **제안**: 어떻게 수정해야 하는지
- **근거**: 왜 문제인지

이슈가 없으면 "이슈 없음"으로 표기.
마지막에 전체적인 {관점} 평가를 한 문단으로 요약.
```

**중요**: 3개 에이전트를 하나의 메시지에서 병렬로 스폰한다 (순차 아님).

## Phase 3: 결과 종합

3개 에이전트의 결과를 수집한 후 심각도별로 통합 테이블을 생성:

```markdown
## Critical (N건)
## Major (N건)
| # | 관점 | 이슈 | 파일 |

## Minor (N건)
| # | 관점 | 이슈 |

## Nit (N건)
```

## Phase 4: 수용/거절 판단 (Triage)

시니어 엔지니어 관점에서 각 이슈를 독립적으로 판단한다.

### 판단 전 필수 검증

리뷰어가 언급한 코드를 **실제로 Read**하여 전제가 맞는지 확인한다.

### 분류

| 분류 | 기준 |
|------|------|
| **수용** | 기술적으로 타당 + 코드 확인됨 + 구현 비용 합리적 |
| **거절** | 아래 근거 중 하나 이상 해당 |

### 거절 가능 근거

- **YAGNI**: 현재 불필요한 방어 코드 또는 추상화
- **과도한 설계**: 복잡도 대비 가치 낮음
- **기존 결정 충돌**: 플랜/설계에서 이미 의도적으로 결정된 사항
- **관심사 분리**: 애플리케이션이 아닌 인프라/CI에서 처리할 사항
- **업계 표준 관행**: 테스트 코드 등에서 보편적으로 허용되는 패턴
- **디버깅 능력 저하**: 운영 디버깅에 필수적인 정보를 제거하는 제안

### 출력 형식

```markdown
### 수용 (N건)
| # | 이슈 | 수용 근거 |

### 거절 (N건)
| # | 이슈 | 거절 근거 |
```

## Phase 5: 수용건 코드 반영

수용된 이슈를 실제 코드에 반영한다.

1. Edit tool로 코드 수정
2. `typecheck` (또는 프로젝트 빌드 명령) 실행
3. 관련 테스트 실행
4. 전체 테스트 실행하여 regression 없음 확인

**모든 검증이 통과해야 다음 Phase로 진행.**

## Phase 6: 재리뷰 요청

수정된 코드와 거절 사유를 새 oracle 에이전트에게 전달하여 재리뷰를 요청한다.

### 재리뷰 프롬프트 구성

```
당신은 **{관점} 전문 코드 리뷰어**입니다.

## 수용 항목 (코드 반영 완료)
{수용 항목 목록 + 반영 내용 요약}

## 거절된 항목과 거절 사유
{각 거절 항목 + 상세 거절 사유}

## 재리뷰 요청
수정이 반영된 최신 코드를 읽고:
1. **거절 사유 재평가**: [수긍/이의제기] + 판단 근거
2. **수용 반영 확인**: 올바르게 반영되었는지 PASS/FAIL
3. **추가 이슈**: 수정 과정에서 새로 발생한 이슈

## 리뷰할 파일
{최신 파일 목록}
```

### 재리뷰 결과 처리

- **거절 수긍**: 해당 항목 확정 종료
- **이의제기 (blocking)**: 재검토 후 수용 여부 재판단
- **이의제기 (non-blocking)**: 빠르게 반영 후 진행
- **수용 반영 FAIL**: 즉시 수정
- **추가 이슈 발견**: Phase 4로 복귀하여 triage

## Phase 7: 결과 보고

사용자에게 최종 결과를 보고한다.

```markdown
## 코드 리뷰 완료

### 수용 반영 (N건)
| # | 이슈 | 조치 |

### 거절 확정 (N건)
| # | 이슈 | 거절 근거 |

### 검증 결과
- 타입체크: PASS/FAIL
- 테스트: N개 통과
```
