# Expert Code Review

코드 변경사항에 대한 3인 전문가 병렬 리뷰 → 수용/거절 판단 → 코드 반영 → 재리뷰 사이클.

## Workflow

```
코드 변경 파악 → REVIEW (3 oracle 병렬) → TRIAGE (수용/거절) → IMPLEMENT (수용건 반영)
                                                                    ↓
                                   RE-REVIEW (거절 사유 검증 + 반영 확인, 최대 2회) → 완료
```

## 원칙

- **리뷰어에게 변경의 의도와 범위를 준다.** 의도를 모르는 리뷰어는 의도된 결정을 이슈로 올리고 변경 범위 밖의 기존 코드를 지적한다. 그 노이즈를 트리아지에서 걸러내는 것보다 리뷰 단계에서 만들지 않는 것이 싸다.
- **모든 발견은 인용과 실패 시나리오를 갖는다.** "어떤 입력에서 어떤 잘못된 결과가 나는가"를 쓸 수 없는 지적은 Nit다. 이 규칙이 트리아지의 검증 시간을 줄이고 추측 기반 지적을 걸러낸다.
- **리더는 리뷰어를 기다리는 동안 기준선을 만든다.** 반영 후 검증에서 "원래 깨져 있던 것"과 "내가 깨뜨린 것"을 구분할 근거가 된다.

## Phase 1: 리뷰 대상 파악

**1. 변경 범위 확정**

사용자가 파일을 지정하지 않은 경우, 리뷰 기준점(base)을 정하고 변경 파일을 수집한다. worktree 안에서 작업 중이면 그 디렉토리에서 실행한다.

```bash
# 브랜치 작업을 리뷰할 때 (기본): main과의 merge-base 기준
git diff --name-status $(git merge-base origin/main HEAD)...HEAD
# 아직 커밋하지 않은 작업만 리뷰할 때
git diff --name-status HEAD
# 새로 추가했지만 아직 add하지 않은 파일 — diff에 안 잡히므로 반드시 함께 본다
git status --porcelain | grep '^??'
```

어떤 기준점을 썼는지 기록해둔다 — 리뷰어에게 같은 기준점을 준다.

**2. 변경 의도 수집**

다음을 모아 `<change_intent>`로 정리한다:
- 이슈/PR 링크와 제목, 플랜 문서 경로 (`docs/plans/issue-*.md` 등)
- 플랜이나 대화에서 의도적으로 결정한 사항 (예: "재시도는 인프라에서 처리하므로 앱 코드에 넣지 않음")
- 이번 변경에서 다루지 않기로 한 것

**3. 파일 읽기**

변경 파일과 관련 인터페이스·테스트·설정 파일을 읽는다. 서로 독립이므로 한 번에 병렬로 읽는다.

## Phase 2: 3인 전문가 병렬 리뷰

Agent tool로 3개의 `oracle` 에이전트를 **동시에** 스폰한다. 각 에이전트는 서로 다른 전문 관점을 가진다.
`oracle`이 현재 환경의 에이전트 목록에 없으면 (`.claude/agents/` 미정의) `general-purpose`로 스폰한다. 아래 프롬프트 템플릿의 `<rules>`에 읽기 전용 규칙이 들어 있으므로 그대로 쓴다 (Phase 6 재리뷰도 동일).

### 리뷰어 구성

변경의 도메인에 따라 기본 구성을 고른다. 사용자가 관점을 지정하면 그 구성으로 바꾼다.

| 도메인 | 리뷰어 1 | 리뷰어 2 | 리뷰어 3 |
|--------|---------|---------|---------|
| **백엔드** (기본) | 보안/에러처리 — 취약점, 인젝션, PII 노출, API 키 보호, 예외 처리 누락, 로깅 보안 | 코드품질/패턴 — 프로젝트 패턴 준수, DI, 중복, 타입 안정성, 아키텍처 정합성 | 테스트 — 누락 분기, stub 전략, 엣지 케이스, flaky 위험 |
| **프론트엔드** | 상태/렌더링 — 상태 관리 정합성, 불필요한 리렌더, 로딩·에러 상태, 접근성 | 코드품질/패턴 — 컴포넌트 구조, 훅 규칙, 디자인 시스템 준수 | 테스트 — 사용자 시나리오 커버리지, 모킹 경계, 회귀 |
| **인프라/배포** | 보안/권한 — 최소 권한, 시크릿 노출, 네트워크 경계 | 가용성/롤백 — 배포 실패 시 복구 경로, 마이그레이션 순서, 다운타임 | 관측/비용 — 로그·알람 공백, 비용 급증 경로 |

프론트엔드와 백엔드가 함께 바뀌면 백엔드 구성을 쓰고 리뷰어 2에 "프론트엔드 변경도 같은 기준으로 본다"를 덧붙인다.

### 에이전트 프롬프트 템플릿

컨텍스트(의도·범위)를 위에, 지시와 출력 형식을 아래에 둔다.

```
당신은 **{관점} 전문 코드 리뷰어**입니다. 아래 변경을 {관점} 관점에서 리뷰합니다.

<change_intent>
{이슈/PR 링크와 제목, 플랜 경로}
의도적으로 결정된 사항: {목록 — 재검토 대상이 아니라 전제다}
이번 변경에서 다루지 않는 것: {목록}
</change_intent>

<review_scope>
기준점: {base ref, 예: merge-base origin/main...HEAD, 또는 "HEAD 기준 미커밋 변경"}
변경 파일: {경로 목록 + 각 한 줄 설명}
참조 코드 (비교용, 변경 대상 아님): {인터페이스, 유사 구현체, 테스트 패턴}
</review_scope>

<review_focus>
{해당 리뷰어의 체크포인트 목록}
</review_focus>

<rules>
- 열지 않은 코드에 대해 추측하지 않는다. 지적하려는 파일은 반드시 Read하고, 변경 전후를 보려면 위 기준점으로 `git diff`를 직접 실행한다.
- 이번 변경이 건드리지 않은 기존 코드의 문제는 발견 목록이 아니라 마지막 "후속 제안" 절에 따로 적는다. 리뷰 대상은 이번 변경이다.
- 방어 코드·추상화·설정 가능성을 제안할 때는 그것이 없어서 실제로 발생하는 시나리오를 함께 적는다. 시나리오를 쓸 수 없으면 Nit다.
- 읽기 전용이다. 파일을 수정하거나 생성하지 않고 텍스트로만 보고한다.
</rules>

<output_format>
각 이슈를 아래 형식으로 작성:

### [심각도: Critical/Major/Minor/Nit] 이슈 제목
- **파일**: 경로:줄번호
- **인용**: 문제가 되는 코드 1~5줄을 그대로
- **실패 시나리오**: 어떤 입력·상태에서 어떤 잘못된 결과가 나는지 구체적으로
- **제안**: 어떻게 수정할지
- **근거**: 왜 문제인지 (프로젝트 컨벤션이면 근거 파일 경로)

심각도 기준: Critical = 데이터 손상·보안 침해·운영 장애로 이어짐 / Major = 기능 오동작 또는 명백한 컨벤션 위반 / Minor = 동작엔 영향 없지만 유지보수 비용 / Nit = 취향 또는 시나리오 없는 제안.

이슈가 없으면 "이슈 없음"으로 표기.
그 다음 "## 후속 제안" 절에 변경 범위 밖에서 발견한 것을 적는다 (없으면 생략).
마지막에 전체적인 {관점} 평가를 한 문단으로 요약.
</output_format>
```

3개 에이전트는 하나의 메시지에서 병렬로 스폰한다. 서로 독립이라 순차로 돌릴 이유가 없고, 리뷰 시간이 그만큼 줄어든다.

### 리뷰어가 도는 동안 리더가 할 일

스폰 후 결과를 기다리며 멈추지 않는다. 그 사이에:

1. 해당 레포 CLAUDE.md에서 typecheck·lint·test 명령을 확인하고 **기준선을 실행**한다 — 지금 상태에서 무엇이 통과하고 무엇이 실패하는지 기록한다. 실행 디렉토리는 해당 레포(또는 worktree).
2. 플랜 문서와 이슈를 다시 읽어 Phase 4 트리아지에 쓸 "의도된 결정" 목록을 손에 든다.

## Phase 3: 결과 종합

3개 에이전트의 결과를 수집한 후 심각도별로 통합 테이블을 생성한다. 같은 이슈를 2명 이상이 지적했으면 표시한다 — 트리아지에서 가중치를 둘 근거가 된다. 각 리뷰어의 "후속 제안"은 별도로 모아둔다 (트리아지 대상이 아니라 Phase 7에서 그대로 전달).

```markdown
## Critical (N건)
## Major (N건)
| # | 관점 | 이슈 | 파일 | 중복 지적 |

## Minor (N건)
| # | 관점 | 이슈 |

## Nit (N건)
```

## Phase 4: 수용/거절 판단 (Triage)

시니어 엔지니어 관점에서 각 이슈를 독립적으로 판단한다.

### 판단 전 필수 검증

리뷰어가 인용한 코드가 **실제로 그 위치에 그 내용으로 있는지 Read로 확인**하고, 실패 시나리오가 현재 코드에서 정말 재현 가능한지 따라가 본다. 인용이 틀렸거나 시나리오가 성립하지 않으면 거절 근거가 된다.

### 분류

| 분류 | 기준 |
|------|------|
| **수용** | 기술적으로 타당 + 코드 확인됨 + 구현 비용 합리적 |
| **거절** | 아래 근거 중 하나 이상 해당 |

### 거절 가능 근거

- **전제 오류**: 인용이 실제 코드와 다르거나 실패 시나리오가 성립하지 않음
- **YAGNI**: 현재 불필요한 방어 코드 또는 추상화
- **과도한 설계**: 복잡도 대비 가치 낮음
- **기존 결정 충돌**: `<change_intent>`에 적힌 의도적 결정 사항
- **관심사 분리**: 애플리케이션이 아닌 인프라/CI에서 처리할 사항
- **업계 표준 관행**: 테스트 코드 등에서 보편적으로 허용되는 패턴
- **디버깅 능력 저하**: 운영 디버깅에 필수적인 정보를 제거하는 제안

거절 근거는 재리뷰에서 리뷰어가 반박할 수 있게 구체적으로 쓴다. "불필요함" 한 줄은 근거가 아니다.

### 출력 형식

```markdown
### 수용 (N건)
| # | 이슈 | 수용 근거 |

### 거절 (N건)
| # | 이슈 | 거절 근거 |
```

이 표를 **사용자에게 먼저 출력한 뒤** Phase 5로 넘어간다. 응답을 기다리지는 않지만, 사용자가 잘못된 수용·거절을 중간에 바로잡을 기회를 준다.

## Phase 5: 수용건 코드 반영

1. **수용 항목만 고친다.** 같은 파일에서 눈에 띄는 다른 개선점은 건드리지 않고 Phase 7의 후속 제안에 적는다.
2. 파일 전체를 다시 쓰지 않고 해당 위치만 Edit한다.
3. 검증 명령은 Phase 2에서 확인한 레포 CLAUDE.md의 명령을 그대로 쓴다 (typecheck → 관련 테스트 → 전체 테스트). 실행 디렉토리는 해당 레포(또는 worktree).
4. 결과를 기준선과 비교한다. 기준선에서 이미 실패하던 테스트는 이번 변경의 회귀가 아니므로 보고에 "기존 실패"로 표시하고, 새로 실패한 것만 고친다.
5. **커밋하지 않는다.** 커밋 여부와 메시지는 사용자가 정한다.

새로 생긴 실패가 남아 있으면 다음 Phase로 가지 않는다.

## Phase 6: 재리뷰 요청

수정된 코드와 거절 사유를 **새** oracle 에이전트에게 전달한다. 재리뷰의 목적은 트리아지의 확증 편향을 잡는 것이다.

### 재리뷰 프롬프트 구성

```
당신은 **{도메인} 시니어 코드 리뷰어**입니다. ({도메인}은 Phase 2 리뷰어 구성의 도메인)

<change_intent>
{Phase 2와 동일}
</change_intent>

<accepted>
{수용 항목 + 반영 내용 요약 + 수정된 파일:줄}
</accepted>

<rejected>
{각 거절 항목 + 거절 사유 — 리뷰어가 반박할 수 있게 구체적으로}
</rejected>

<task>
수정이 반영된 최신 코드를 읽고:
1. 거절 사유 재평가: 항목마다 [수긍 / 이의제기-blocking / 이의제기-non-blocking] + 판단 근거.
   blocking은 그대로 두면 Critical/Major 결과가 실제로 발생하는 경우에만 쓴다.
2. 수용 반영 확인: 항목마다 PASS/FAIL. FAIL이면 무엇이 빠졌는지.
3. 추가 이슈: 수정 과정에서 새로 생긴 문제만, Phase 2와 같은 인용·실패 시나리오 형식으로.
</task>

<rules>
- 열지 않은 코드에 대해 추측하지 않는다. 판단하려는 파일은 반드시 Read한다.
- 읽기 전용이다. 파일을 수정하거나 생성하지 않고 텍스트로만 보고한다.
</rules>
```

### 재리뷰 결과 처리

- **거절 수긍**: 해당 항목 확정 종료
- **이의제기 (blocking / non-blocking 모두)**: Phase 4와 같은 기준으로 재판단한다. non-blocking이라고 자동 반영하지 않는다 — 리뷰어의 이의가 트리아지 기준을 통과하면 수용, 아니면 거절 근거를 보강한다
- **수용 반영 FAIL**: 즉시 수정 후 Phase 5의 검증을 다시 돈다
- **추가 이슈 발견**: Phase 4로 복귀하여 triage

**루프 상한**: 재리뷰는 최대 2회. 2회 후에도 남은 이의제기나 추가 이슈는 더 돌리지 않고 Phase 7 보고의 "미해결" 표로 사용자에게 넘긴다. 같은 결정을 반복해서 다시 여는 것보다 사용자 판단으로 넘기는 것이 낫다.
